# v0.4 NIA v2.1 and Policies/Procedures/Guidelines Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add NIA v2.1 as a second framework that shares evidence with ISO 27001 through a mapping (licence-safe, with customer-side import of the official text), a policies/procedures/guidelines register linked to controls, and the Compliance-page changes (Themes/Domains button).

**Architecture:** NIA lives in the existing framework-agnostic catalogue: one `Framework`, `Requirement` rows for domains and controls, and `ControlRequirement` links to ISO controls (the mapping). NIA status is computed from the linked controls in a small `assayr.nia` service; NIA-only controls are ordinary Assayr controls coded `NIA <ref>`. Documents are a new `assayr.documents` module (two tables, one migration) using the existing blob store. The frontend adds a framework switch, NIA pages, a Policies page and three collapsible document sections on every control page.

**Tech Stack:** FastAPI, SQLAlchemy 2, Alembic, pypdfium2; React 19, TanStack Router/Query, Tailwind v4; pytest, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-16-v0.4-nia-and-documents-design.md`

## Global Constraints

- No NCSA prose in the repository or the product: only control IDs, domain codes, domain names and our own one-line domain summaries. Imported text is stored per install only.
- Framework row: `Framework(code="nia-2.1", name="NIA", version="2.1")`; dashboard/compliance display name **NIA v2.1** in bold.
- 26 domains: IG, RM, TM, DL, CM, PS, SA, IM, BC, SM, DR, DC, AC, CS, NS, IE, GS, PR, SS, SU, MS, AM, CY, OS, PH, VL.
- Derived NIA status: all mapped compliant → compliant; any non-compliant → non-compliant; else least advanced of (not_started < in_progress < in_review < at_risk < compliant).
- NIA-only control code: `NIA <ref>` (e.g. `NIA AC 3`), theme = domain name.
- Document types exactly `policy`, `procedure`, `guideline`; statuses `draft`, `approved`, `retired`; review due one year after approval by default.
- Mapping, applicability, import and approval require ISMS-manager rights; reading requires `controls:read`.
- Seeding is idempotent and runs on upgrade (Windows `finish-upgrade`, Linux container start).
- Commits carry no Co-Authored-By trailer; use explicit `git add <paths>` (never `-A`); keep `.gitignore` intact.

## Review Focus

1. **An install upgraded from 0.3.x** — NIA appears after upgrade without manual steps (seed runs), existing ISO data untouched; test in Task 2 (seed on a populated DB) and Task 12 (finish_upgrade runs seed).
2. **An NIA control mapped to an excluded ISO control** — excluded mapped controls are ignored for status; if all mapped controls are excluded the NIA control shows "not started" until its own applicability is decided; test in Task 3.
3. **A PDF that is not NIA v2.1** (another version or another document) — import refuses with the version found and changes nothing; test in Task 5.
4. **A document linked to a control the user cannot see / a deleted control** — links cascade on delete; lists only show controls in the user's scope; test in Task 7.
5. **Two documents with the same reference code** — refused with a clear message (unique per scope); test in Task 7.
