# v0.8: ISO/IEC 42001 and SOC 2 Type 2 — design

Status: approved in conversation 2026-10-17 (answers: own controls with sharing; AI register with impact
assessment; SOC 2 criteria with tested Type 2 audits; one release v0.8.0).

## Goal

Let an organisation run its AI management system (ISO/IEC 42001:2023) and prepare for a SOC 2 Type 2
examination (Security category) in the same on-premise Assayr that already runs ISO 27001, NIA and
PDPPL, reusing evidence instead of collecting it again.

## Sources and content rules

- `ISO 42001 standard.pdf` (scanned copy of ISO/IEC 42001:2023) and `SOC2 Type 2 Compliance
  Tracker.xlsx` (the user's tracker: Security category, CC1–CC9, 139 control activities with
  "Detailed Test of Controls" and "Test Results") are reference material only.
- Assayr ships requirement IDs, short headings (as it already does for ISO 27001) and summaries written
  for Assayr. It never ships ISO text, AICPA criteria text or points of focus, or text from the user's
  workbook. Workbook text enters a database only when the user imports their own file.
- Tests and fixtures use invented text.

## Scope

In: ISO/IEC 42001 framework and controls; SOC 2 Security (common criteria CC1.1–CC9.2) framework and
controls; mapping to ISO 27001 controls for shared evidence; AI systems register; AI system impact
assessment; SOC 2 Type 2 audits with observation period and test results; tracker import/export;
42001 internal audits; dashboard, compliance and controls UI.

Out (later): SOC 2 additional categories (Availability, Confidentiality, Processing Integrity,
Privacy); a SOC 2 report generator; auditor (external CPA) accounts; AI model monitoring integrations.

## 1. Frameworks and controls

### Catalogue data

- `catalogue/data/iso42001_2023.json`: framework `iso42001`, name "ISO/IEC 42001", version "2023".
  - Clauses 4–10 with sub-clauses (same shape as `iso27001_clauses.py`), including the AI-specific
    ones: 6.1.2 AI risk assessment, 6.1.3 AI risk treatment, 6.1.4 AI system impact assessment,
    8.2 AI risk assessment, 8.3 AI risk treatment, 8.4 AI system impact assessment.
  - Annex A objectives A.2–A.10 (kind `theme`) and the 38 controls (kind `annex_control`):
    A.2.2–A.2.4, A.3.2–A.3.3, A.4.2–A.4.6, A.5.2–A.5.5, A.6.1.2–A.6.1.3, A.6.2.2–A.6.2.8,
    A.7.2–A.7.6, A.8.2–A.8.5, A.9.2–A.9.4, A.10.2–A.10.4.
  - Each control: `ref`, `title` (heading), `objective` (A.x), `summary` (own words, one or two
    sentences), `evidence_hint` (what an auditor would expect to see), `iso27001` (list of mapped
    ISO 27001 refs, may be empty), `auto` (optional automatic check key, see section 3).
- `catalogue/data/soc2_tsc_security.json`: framework `soc2`, name "SOC 2", version "TSC 2017
  (rev. 2022) Security".
  - 9 series (kind `theme`): CC1 Control environment, CC2 Information and communication, CC3 Risk
    assessment, CC4 Monitoring activities, CC5 Control activities, CC6 Logical and physical access,
    CC7 System operations, CC8 Change management, CC9 Risk mitigation.
  - 33 criteria (kind `criterion`): CC1.1–CC1.5, CC2.1–CC2.3, CC3.1–CC3.4, CC4.1–CC4.2, CC5.1–CC5.3,
    CC6.1–CC6.8, CC7.1–CC7.5, CC8.1, CC9.1–CC9.2. Each with own `summary`, `evidence_hint`,
    `iso27001` mapping.
- A unit test checks both files: expected counts (42001: 38 Annex A controls; SOC 2: 33 criteria),
  unique refs, every mapped ISO ref exists in the ISO 27001 catalogue, no summary longer than 400
  characters.

### Control model

- `Control.framework` (String(20), not null, server default `iso27001`), values `iso27001`,
  `nia`, `iso42001`, `soc2`. Migration `0011_ai_soc2.py` adds the column and back-fills it
  (`nia` for the existing NIA-only controls coded `NIA <ref>`, `iso27001` for the rest).
- Control codes stay unique per scope (the existing `(scope_id, code)` constraint is kept), following
  the convention NIA-only controls already use: ISO 42001 controls are coded `AI <ref>` (for example
  `AI A.6.2.4`, `AI 6.1.4`) because their refs collide with ISO 27001 refs; SOC 2 codes (`CC6.1`,
  `CC6.1.12`) do not collide and are used as they are. Every lookup by code (control page URL,
  risk/document/NIA links) therefore stays unambiguous. The UI shows the ref without the `AI ` prefix
  next to a framework chip.
- `iso_controls()` becomes `Control.framework == "iso27001"`, and the dashboard's `"NIA "` prefix
  checks use the column.
- Every existing query over controls that means "the ISO 27001 controls" (controls list, SoA, scoring,
  dashboard ISO row, NIA mapping and seed, audits catalogue for ISO, risk and document links, PDPPL
  evidence checks) filters `framework == "iso27001"` unless the caller passes another framework.
  A test per module guards that 42001/SOC 2 controls do not leak into ISO 27001 views or counts.
- Seeding per scope (idempotent, runs at start-up like the existing seeds):
  - 42001: one control per clause leaf and per Annex A control, code = `AI <ref>`, theme = objective
    or clause group.
  - SOC 2: one control per criterion, code = ref (e.g. `CC6.1`), theme = series.
  - Each seeded control gets an evidence slot like ISO controls do, and a `ControlRequirement` to its
    requirement.
- Status, applicability (with exclusion reason), owners, review frequency and evidence work exactly as
  for ISO 27001 controls; scoring reuses the same rules.

### SOC 2 control activities

- An organisation's control activities (from the tracker or typed in) are controls with
  `framework = "soc2"`, code = their number (e.g. `CC6.1.12`), mapped to the criterion in their
  number (`CC6.1`). The criterion control's status is derived from its activities when it has any
  (worst-of rule used by NIA: non-compliant wins, else least advanced); with no activities it is
  managed directly.
- Control activities carry `description` (the control text) and a `test_procedure` (new nullable
  Text column on control, used only by SOC 2).
- Users can add, edit and retire activities from the SOC 2 view (`controls:write`).

## 2. Shared evidence through mapping

- `GET /controls/{id}/related` returns the mapped controls in other frameworks (42001/SOC 2 ↔ ISO
  27001, from the JSON mapping) with their current status and their latest accepted evidence versions.
- `POST /controls/{id}/reuse-evidence` with `{version_id}` links an existing artefact version from a
  related control into this control's slot (creates an `ArtefactLink`; no file copy). Only versions
  linked to a related control in the same scope can be reused; otherwise 422. Verification runs on the
  new link as for any link.
- Control page: a "Related controls" panel listing mapped controls, their status badge, and per
  evidence item a "Reuse" button (hidden when already linked).

## 3. AI systems module (`assayr.ai`)

### Register

- `ai_system`: `code` (AIS-001…, per scope), `name`, `purpose`, `owner_id`, `source`
  (`in_house` | `third_party` | `open_source`), `provider` (nullable), `model_type` (free text, e.g.
  "classification", "LLM"), `lifecycle` (`planned` | `development` | `validation` | `deployed` |
  `retired`), `risk_level` (1–5, shown Very low…Very high with LevelBadge), `uses_personal_data`
  (bool), `pii_categories` (list, same vocabulary as assets), `asset_ids` (links to assets),
  `human_oversight` (text), `status` (`active` | `retired`), timestamps.
- Permissions: new `ai:manage` for `isms_manager` (the platform admin role manages users and
  settings only, as elsewhere); read for anyone with `controls:read`.
- List page "AI systems" with a status bar by lifecycle, filters, and the register table; detail page
  with edit form.

### AI system impact assessment (AIIA)

- `ai_impact_assessment` (one per AI system, same lifecycle as the DPIA):
  sections (text): intended use and foreseeable misuse; affected individuals and groups; impacts on
  individuals; societal impacts; fairness and bias; transparency and explainability; human oversight;
  safety and reliability; data quality and provenance; conclusion.
- Impacts: rows with description, area (one of the sections), likelihood 1–5, impact 1–5, score
  L×I, mitigation; "Raise to risk register" creates a risk once (idempotent, as DPIA does).
- Workflow (as the DPIA): `draft` → `in_review` → `approved`; `reopen` returns an approved
  assessment to `draft` and clears the approval. Submit needs every section filled and at least one
  impact row (409 otherwise, naming what is missing); approve needs `ai:manage`.

### Automatic 42001 checks

- Some 42001 controls carry an `auto` key evaluated live (as PDPPL does) and shown on the control as
  "Assayr check: met / not met" with the reason; they do not overwrite the manual status but feed
  the dashboard hint:
  - `ai_register`: at least one AI system recorded (A.4.2, A.6.2.7 documentation hints).
  - `aiia_all`: every deployed AI system has an approved impact assessment (A.5.2, A.5.3, 6.1.4, 8.4).
  - `aiia_fresh`: approved assessments are less than 12 months old (A.5.2).
  - `ai_owner`: every active AI system has an owner (A.3.2).
  - `ai_risks`: high impacts (score ≥ 15) are raised to the risk register (6.1.3, 8.3).

## 4. Audits: SOC 2 Type 2 and ISO 42001

- `Audit.framework` accepts `iso27001`, `nia-2.1`, `iso42001`, `soc2`. For `soc2`, period start
  and end are required and end must be on or after start (this also fixes the deferred "start after
  end" minor for all frameworks: 422 when end < start).
- Audit rows for SOC 2 are control activities (and criterion controls with no activities). Extra row
  fields (nullable, used for SOC 2): `test_procedure`, `population` (text), `sample_size` (int ≥ 0),
  `samples_tested` (int ≥ 0, ≤ sample size), `exception_note`.
- SOC 2 results: `no_exception`, `exception`, `not_tested` (added to the result enum; ISO/NIA keep
  pass/partial/fail/na; `audit_item.result` widens to String(20)). A result must belong to the audit's
  framework (422 otherwise). An `exception` needs an exception note.
- Summary for SOC 2: counts by result per series and overall, shown with the status bar
  (no exception = success, exception = danger, not tested = neutral).
- Import (`POST /audits/import`, framework `soc2`): reads the tracker layout — section headings,
  "Criteria:" rows, header row "Control Number | Controls | Detailed Test of Controls | Test
  Results", continuation rows with an empty number append to the previous activity's test text.
  Creates or updates the SOC 2 control activities (code, description, test procedure) and a draft
  audit with one row per activity; a "Test Results" cell starting with "No exceptions" maps to
  `no_exception`, one containing "exception" to `exception`, empty to unset. Report lists skipped
  rows with the reason (as the NIA import does).
- Export: the same layout, grouped by series with "Criteria:" rows showing the criterion ID and
  Assayr's summary (never AICPA text), and Test Results written as "No exceptions noted." /
  "Exception noted: <note>" / "Not tested".
- 42001 internal audit: same as ISO audits (pass/partial/fail/na) over 42001 controls, sheet
  "ISO 42001 - IA report".

## 5. UI

- Controls page: framework switcher (segmented control) ISO 27001 · NIA v2.1 · ISO 42001 · SOC 2,
  in the URL as `?framework=`. 42001 groups by clause/objective; SOC 2 groups by series, criteria
  rows expandable to their activities, with "Add activity".
- Control detail: shows framework chip, Related controls panel, Assayr check (42001 auto), and
  test procedure (SOC 2 activities).
- Dashboard and Compliance: framework rows "ISO/IEC 42001" and "SOC 2 (Security)" with percent and
  status bar, clickable to the controls page with the right framework.
- Navigation: "AI systems" between Assets and Privacy.
- Audits: framework select adds ISO 42001 and SOC 2; SOC 2 audit page shows period, per-row sample
  fields and the SOC 2 results.
- All statuses use the shared `Status` registry: add areas `aiLifecycle`, `aiia`, `soc2Result`.

## 6. Error handling

- Import with no recognised control numbers: 422 "None of the rows in this workbook are SOC 2
  control numbers (like CC6.1.2)."
- Activity number whose criterion does not exist (e.g. `CC10.1.1`): skipped and reported.
- Reuse of evidence not linked to a related control: 422.
- Deleting an AI system with an approved assessment: not allowed; retire it instead (409).
