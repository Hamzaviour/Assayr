# v0.4 — NIA v2.1 alongside ISO 27001, and policies / procedures / guidelines — design

Date: 2026-10-16
Status: approved in conversation (NIA design, licence approach, mapping approach, dropdown placement);
awaiting spec review
Sources: `NCSA_CSGA_ National_Information_Assurance_Standard_En_V2.1_1.pdf` (54 pages, 26 domains),
`guidance-NIA_manual_english_v2.0_0 1.pdf`, the user's `PP - Internal Audit Report - v1.0.xlsx`.

## Goals

1. NIA v2.1 is a second framework in Assayr, sharing evidence with ISO/IEC 27001 through a mapping.
2. Licence-safe: no NCSA text ships in the product (NCSA requires written authorisation for commercial
   reproduction, standard page 3). Customers import the official text from their own copy.
3. Policies, procedures and guidelines are managed documents linked to controls; each control shows them in
   three collapsible sections, and a Policies page lists them the same way.
4. Compliance page: the Annex A themes list leaves the card and opens from a separate "Themes" button.

Out of scope (later releases): internal audit reports (Pass/Fail/Partial per control, the Excel layout),
policy acknowledgement by employees, training & awareness.

## 1. NIA in the catalogue

The catalogue is already framework-agnostic: `Framework` → `Requirement` (ref, title, kind, parent) and
`ControlRequirement(control, requirement, coverage full|partial)`.

- Seed a `Framework(code="nia-2.1", name="NIA", version="2.1")`.
- Seed one `Requirement(kind="domain")` per NIA domain (26: IG, RM, TM, DL, CM, PS, SA, IM, BC, SM, DR, DC,
  AC, CS, NS, IE, GS, PR, SS, SU, MS, AM, CY, OS, PH, VL) with its name (factual labels) and a one-line
  summary of the domain written by us.
- Seed one `Requirement(kind="control")` per NIA control ID (e.g. `NS 12`) under its domain, title
  `"<ID> · <domain name>"` until the official text is imported. Control IDs and the domain structure are
  facts, not NCSA prose.
- The shipped catalogue data lives in `backend/src/assayr/catalogue/data/nia_v2_1.json`
  (`{domains: [{code, name, summary}], controls: [{ref, domain}], mapping: [{ref, iso: [codes], coverage}]}`).

### Mapping and shared evidence

- `mapping` links each NIA control to the ISO Annex A controls that cover it (`ControlRequirement` rows with
  `coverage` full or partial). It is our own analysis, IDs only, produced by reading each control statement
  and choosing the matching ISO controls; reviewed before release.
- An NIA control's status is derived from its mapped ISO controls:
  - all mapped controls compliant → compliant;
  - any non-compliant → non-compliant;
  - otherwise the "least advanced" status among them (not started < in progress < in review < at risk <
    compliant), so partial progress shows;
  - NIA controls with **no** ISO equivalent get their own Assayr control (`code = "NIA <ref>"`, theme =
    domain name) with one generic evidence slot, scored like any control.
- Readiness for NIA = the share of in-scope NIA controls that are compliant, plus the same weighted score
  model used for ISO (each NIA control's score = average of its mapped controls' scores).
- The ISMS manager can change the mapping (add/remove ISO controls, full/partial) from the NIA control page;
  changes are audited.

### Applicability

Each NIA control can be marked not applicable with a justification (same pattern as the SoA exclusion);
excluded NIA controls leave the NIA totals. ISO exclusions do not exclude NIA controls automatically.

### Importing the official text

Settings → Frameworks → "Import NIA text": an administrator uploads their own copy of the NCSA PDF.

- Assayr extracts text with pypdfium2 (already bundled), finds control statements by ID pattern
  (`<two-letter domain> <number>. <text>` up to the next ID or heading), and domain objectives.
- It checks the document identifies itself as version 2.1; otherwise it refuses with the version found.
- It reports how many controls matched / were not found; matched text is stored in that install only
  (`Requirement.guidance`, plus `attributes.text_source = "imported"`); re-import replaces it.
- The PDF itself is not kept.

## 2. Policies, procedures and guidelines

A document register (the existing nav item "Policies", today "soon"):

- `Document`: type (`policy` | `procedure` | `guideline`), title, reference code (e.g. `POL-01`), owner, status
  (`draft` → `approved` → `retired`), version label, approved by / on, next review date, current file
  (stored in the evidence blob store, so backups include it), description.
- `DocumentControl`: links a document to controls (ISO or NIA-only controls); a document can support many
  controls.
- Approval: an ISMS manager approves a draft (audited); editing an approved document's file creates a new
  draft version. Review date defaults to one year after approval; documents past review show "Review due".
- Linking an approved policy to a control's "policy" evidence slot is out of scope (evidence stays evidence);
  the document list is about the documents themselves.

### Where documents appear

- **Policies page** (`/policies`): three collapsible sections — **Policies**, **Procedures**,
  **Guidelines** — each listing its documents (code, title, owner, status, version, next review), with search
  and "New document". Opening a document shows details, file download, linked controls, history.
- **Control page** (ISO and NIA): three collapsible sections — Policies, Procedures, Guidelines — listing the
  documents linked to that control, each with a "Link a document" action (searchable picker). Empty sections
  say so ("No procedures linked yet").

## 3. Compliance page and dashboard

- Compliance page: one card per framework (**ISO/IEC 27001**, **NIA v2.1**), names bold. The theme/domain
  breakdown no longer sits inside the card; a **"Themes"** button (ISO) / **"Domains"** button (NIA) on each
  card opens the breakdown as a collapsible panel below it.
- Dashboard: the NIA row appears under ISO in the Compliance section (same layout: bold name, readiness,
  progress bar, status breakdown), linking to the Compliance page. No row before NIA is seeded.
- Controls page: a framework switch (ISO / NIA); for NIA a domain filter and the NIA control list (ref,
  domain, status, mapped ISO controls). NIA control page: summary or imported text, mapped ISO controls with
  their status, shared evidence (read through the mapped controls), applicability, and the three document
  sections.

## API (new)

- `GET /frameworks` (exists) lists NIA once seeded.
- `GET /nia/controls?domain=` and `GET /nia/controls/{ref}`; `PUT /nia/controls/{ref}/mapping`;
  `POST /nia/controls/{ref}/applicability`; `POST /frameworks/nia-2.1/import` (multipart PDF).
- `GET/POST /documents`, `GET/PATCH /documents/{id}`, `POST /documents/{id}/approve`,
  `POST /documents/{id}/file`, `GET /documents/{id}/file`, `PUT /documents/{id}/controls`,
  `GET /controls/{code}/documents` (grouped by type).
- `GET /dashboard` gains the NIA framework row and its groups (domains).

Permissions follow the existing RBAC: reading needs `controls:read`; mapping, applicability, import and
document approval need ISMS-manager rights (`controls:write`); document owners edit their own drafts.

## Data migration

Alembic migration adds `document`, `document_control` (and nothing to existing tables). `assayr seed` loads
NIA idempotently (safe on existing installs; upgrades run seed after migrate — add that to the Windows
`finish-upgrade` and the Linux upgrade path if it is not already there).

## Testing

- Backend: NIA seeding (26 domains, all control refs, idempotent); derived NIA status rules (each case
  above); readiness with exclusions; mapping edit (permissions, audit); PDF import against a generated test
  PDF (matched/unmatched counts, wrong version refused); documents CRUD, approval, review-due, linking,
  grouped per control, permissions; dashboard NIA row.
- Frontend: Compliance cards + Themes/Domains button; dashboard NIA row bold; Controls framework switch and
  NIA list; NIA control page (mapping, applicability); control page document sections; Policies page sections
  and new-document flow.
- Mapping file sanity test: every NIA ref appears once; every mapped ISO code exists.

## Risks

| Risk | Mitigation |
|---|---|
| Mapping quality (260 judgements) | Authored from each control statement, reviewed; editable in the UI; marked "suggested" until reviewed per install |
| PDF layout varies between NCSA prints | Import reports unmatched controls; IDs still work without text |
| Large scope for one release | Build order: NIA catalogue + status → Compliance/dashboard → documents → import |
