# v0.6 — Asset CIA levels, personal data on assets, Data Privacy module — design

Status: approved in conversation 2026-10-16. Builds on v0.5.

## Purpose

Asset owners and auditors read confidentiality, integrity and availability as words, not numbers. Qatar's
Personal Data Privacy Protection Law (PDPPL, Law No. 13 of 2016), ISO/IEC 27001 A.5.34 and the NIA privacy
controls expect the organisation to know which systems hold personal data, what it processes, why, on what
basis, for how long and where it goes. v0.6 adds that knowledge to Assayr: personal data on the asset register
and a Data Privacy module with a record of processing activities and a PII inventory.

Success: a manager marks the HR system asset as holding employee records and national IDs (sensitive auto-set
when health data is added), records the "Payroll" processing activity linked to that asset with lawful basis
"Contract", retention "7 years after leaving", recipients "Bank", cross-border "No"; the Data Privacy page
shows the activity, the PII inventory lists the HR system with its activities, and the Excel export contains both.

## Decisions (from the conversation)

- **5 levels**: Very low, Low, Medium, High, Very high — stored as the existing 1–5 integers (no data change,
  risk scoring unchanged). Criticality = max(C, I, A), shown as a coloured badge.
- **PII on assets: flag + categories + sensitive flag + volume band.**
- **Data Privacy: processing activities (record of processing) + automatic PII inventory + Excel export.**
  No DPIA in this release.

## Levels (shared)

`LEVELS = {1: "Very low", 2: "Low", 3: "Medium", 4: "High", 5: "Very high"}`. API keeps integers and adds
`*_label` fields on output (`confidentiality_label`, `integrity_label`, `availability_label`,
`criticality_label`). Badge colours: Very low = idle grey, Low = ok green, Medium = warn amber,
High = orange (`--heat-4`), Very high = bad red. Asset list filter `criticality=<1..5>` (minimum level).

## Personal data on assets

New `Asset` columns: `holds_pii` (bool, default false), `pii_categories` (JSON list of codes),
`pii_sensitive` (bool), `pii_volume` (`lt100` | `100_1k` | `1k_10k` | `gt10k` | null).

Categories (code → label): `contact` Contact details, `national_id` National ID / QID / passport,
`financial` Financial, `health` Health (sensitive), `biometric` Biometric (sensitive), `hr` Employee / HR
records, `children` Children's data (sensitive), `location` Location, `online` Online identifiers,
`religion` Religious beliefs (sensitive), `criminal` Criminal records (sensitive), `ethnic` Ethnic origin
(sensitive), `other` Other.

Rules: if `holds_pii` is false the other PII fields are cleared; sensitive is forced true when any sensitive
category is present (it may also be set manually); categories validated against the list. Asset list filter
`pii=true` and a "PII" badge. Changes are audited with the existing `asset.update`.

## Data Privacy module

`ProcessingActivity` (per scope): `code` (`PA-001`, sequential), `name`, `purpose`, `data_subjects` (JSON list:
`employees`, `customers`, `suppliers`, `visitors`, `children`, `patients`, `students`, `public`, `other`),
`data_categories` (JSON list, same codes as assets), `lawful_basis` (`consent` | `contract` |
`legal_obligation` | `vital_interest` | `public_interest` | `legitimate_interest`), `recipients` (text),
`cross_border` (bool), `transfer_countries` (text), `retention` (text), `security_measures` (text),
`owner_id`, `status` (`draft` | `active` | `retired`), `review_due` (date), timestamps.

`ProcessingAsset`: `activity_id`, `asset_id` (PK both, cascade). Linking an asset that is not marked as
holding PII marks it (`holds_pii = true`, categories merged) — audited.

`sensitive` on an activity is derived (any sensitive category). `review_overdue` derived
(`review_due < today` and active).

API:
- `GET /privacy/summary` → `{pii_assets, sensitive_assets, activities, active_activities, cross_border,
  reviews_due}`.
- `GET /privacy/activities?q=&status=` · `POST /privacy/activities` · `GET/PATCH /privacy/activities/{id}` ·
  `PUT /privacy/activities/{id}/assets {asset_ids}`.
- `GET /privacy/inventory` → PII assets with categories, sensitive, volume, criticality (+label), owner,
  activity codes/names.
- `GET /privacy/export.xlsx` → sheets "Processing activities" and "PII inventory".

Permissions: reading needs `assets:read`; writing activities needs new `privacy:manage` (isms_manager);
asset PII fields follow the existing asset edit rights (owners of their own assets).

  activities** (table: code, name, lawful basis, subjects, sensitive badge, cross-border badge, assets count,

  asset, categories chips, sensitive, volume, criticality badge, owner, activities); "Export Excel".
